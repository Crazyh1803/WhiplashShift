I've read the plan and the relevant parts of `vehicle.gd`, `race_items.gd` and `proving_ground.gd`. Here's the design.

## Recommendation: keep boost and damage state on `Vehicle`, have `VehicleEffects` only read it

**State to add to `vehicle.gd`** (as public vars next to `power_cut`; use `const` values rather than new `TuningProfile` fields so saved `.tres` files don't change):
```
signal boosted(record: Dictionary)
signal damaged(severity: float)
var boost_charge: int = 0        # 0/1, earned, capped at 1
var boost_time: float = 0.0      # >0 = active (BOOST_TIME ≈ 0.9 s)
var boost_cooldown: float = 0.0  # BOOST_COOLDOWN ≈ 3 s
var damage: float = 0.0          # 0..1, cosmetic only, decays at DAMAGE_DECAY/s
```

**API:**
- **Earning a charge:** grant it inside `_resolve_whiplash`, before `whiplash.emit` (`vehicle.gd:897`), so listeners and the HUD see the new charge. Count it as "clean" only when `retained >= ~0.7`. Doing it inside the vehicle means CPU cars earn charges the same way the player does.
- **`try_boost() -> bool`:** succeeds only if there's a charge, `boost_cooldown <= 0`, `power_cut <= 0`, `engage >= 1` and the car isn't frozen. On success it uses up the charge, sets the timers and emits `boosted`. Add `KEY_Q` next to `KEY_E` in `proving_ground.gd:303`; nothing is bound to Q yet. Also gate it on `RACING`, the same way swap is.
- **Physics:** change one line, `drive_per_wheel` at `vehicle.gd:734`, multiplying it by `(1.0 + BOOST_DRIVE)` while `boost_time > 0 and thr > 0`. It already passes through `gate_open`, `taper` and the friction circle, so top speed and the drive taper stay as they are. Count the timers down in `_tick_timers`. `swap_ends` should set `boost_time = 0` so a boost can't ride through a swap.
- **`apply_cosmetic_damage(severity: float)`:** does `damage = clampf(damage + severity, 0, 1)` and emits `damaged`. Call it from `race_items._apply_hit` right after the impulse (`race_items.gd:599`), after the shield and protection early returns, so blocked hits do nothing. Severity is `data.get("damage", data["loss"])`. Nothing in physics ever reads `damage`.
- **`reset_effects_state()`:** clears all four fields and calls `reset_terrain_response()` and `VehicleEffects.reset()`. Replace the `reset_terrain_response()` calls at `proving_ground.gd:293` and `cpu_driver.gd:297` with it. Clearing the charge on recovery stops players respawning with a boost ready.

**Visuals:** `VehicleEffects` reads `wheels[].contact/slip/spin/normal_load/surface_id`, `active_end`, `forward_vector()`, `boost_time` and `damage`, and listens to `swapped`, `boosted` and `damaged`. It never writes physics state.

## Main tradeoff
Owning the state on the vehicle means a few fields and a few lines added to the force loop. In return, boost goes through the existing drive and traction path, so there's no separate force that could fight the physics tuning.

**Alternative worth considering:** an `item_drive_multiplier` owned by `RaceItems`, set the same way as `item_grip_multiplier`. That keeps `vehicle.gd` almost untouched, but it ties boost to the item system and leaves the proving ground and CPU without it.

## Risks
1. **Effects node gets freed:** `_rebuild_visuals` frees `_visual_root` whenever `apply_vehicle_spec` runs. Add `VehicleEffects` as a direct child of the car in `_build`, the way `VisceraResponse` is added, not under the visual root.
2. **Skid marks and trails across a teleport:** `reset()` has to break trail and skid continuity, or respawning draws a streak from the old position to the new one. Marks already on the ground can stay, but they need a hard cap and should be `top_level`/world-space while still owned by the car, so they're freed with it.
3. **Headless tests:** particle and mesh setup has to work in headless runs and must not change the physics step. Keep `_integrate_forces` free of anything to do with effects.
4. **Two reset paths:** `_place_player` and `cpu_driver` each reset fields by hand. If one of them misses the new call, boost or damage carries over a respawn. Add a test for each path.
5. **CPU asymmetry:** CPU cars will earn charges but never use them unless `cpu_driver` calls `try_boost()`. That's fine for now, but it should be a deliberate choice.
