I couldn't confirm the exact cause: no Godot source or process was available to check, so the first two points below are inference. What I did check: the GLB does carry external `"uri"` images, and the log shows each texture reimported repeatedly within a single run.

**What the evidence says**
- `season-engine.log:593-909` lists the same PNGs (`concrete_normal`, `paving_albedo`, `steel_structure_*`) reimported many times in one import pass. That repeat comes from the 3D-detect mechanism (`detect_3d/compress_to=1`). A scene import that loads a texture through a material queues a texture reimport. The reimport rewrites the sidecar, and each of the 24 GLBs can trigger it again.
- The committed sidecars are already in the post-detect state: `compress/mode=2`, mips on, and an s3tc `path.s3tc`. The rewritten ones are back at defaults with a new UID: `mode=0`, mips off, plain `.ctex`, `vram_texture:false`. Detection only moves a sidecar from default to VRAM, never back. So the sidecar was regenerated from scratch. A rewrite that keeps the UID would not look like this.
- `get_multiple_md5 f.is_null` (log lines 619, 650, 909) fires when an `.import` or its `dest_files` is read while it is being regenerated. It is a symptom of the rewrite, not its cause.
- Your suspicion about `embedded_image_handling=0` is plausible. In Godot 4.x, `gltf/embedded_image_handling` is documented for embedded binary images. External URI images appear to go through the same save/load helper, which for existing resource URIs does `ResourceLoader::load`. That load is what triggers detect and reimport. Setting `0` would not stop it, and `texture_map_mode` doesn't either. I'm not certain of this; I didn't read the 4.7.2 source.

**Ranked hypotheses, each with a check**
1. **The external-URI load path ignores `handling=0` and triggers detect.**
   - Check: copy one GLB with its `"images"` and `"textures"` arrays stripped, import it, and see whether the PNG sidecars still change.
2. **The VRAM sidecars are invalid on the import machine.** For example `import_s3tc_bptc` may be off, or the headless driver can't write VRAM, so Godot discards and regenerates them.
   - Check: look at `rendering/textures/vram_compression/import_s3tc_bptc` in `project.godot`. If it is false, set it to true.
3. **A tool is rewriting the PNGs.** An export touching the PNG mtime or md5 forces a reimport; Godot doesn't reset params on md5 change alone, though.
   - Check: `git status` on the PNGs themselves, and compare md5 before and after the tangent-only GLB update.

**Recommendation**
Make the GLBs geometry-only, which the frozen contract allows:
- Export with no `images`, `textures` or material texture slots. Keep materials as named stubs, such as `mat_paving`, with no texture references.
- Bind the real materials in `city_realism_catalog.gd` by material name from a material library. Load the PNGs as plain `.tres` or `ResourceLoader` resources, never from inside a scene import.
- With no image reference in the scene, the scene importer never loads the PNGs. The detect callback can't fire and the GLB import can't touch the sidecars. This works whichever hypothesis is right.

**Verify**
1. Restore the sidecars, then run `--headless --import` twice.
2. Run `git diff --stat -- godot/assets/city/realism/textures` after each run. It must be empty.
3. Make a tangent-only GLB change and run the import again. The diff must still be empty.
4. Check the log for no repeated `reimport | *.png` lines and no `get_multiple_md5` errors.

I'd skip hypothesis 2 unless step 3 still shows a diff.
