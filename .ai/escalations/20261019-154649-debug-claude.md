**Root cause:** the failing log predates, or is only partly fixed by, the Variant change. `_relevant(peer: Variant)` at `cpu_racecraft.gd:113` already accepts a freed object. The same bug is still present in the two loops that call it:

- `for peer: Vehicle in peers:` is at `cpu_racecraft.gd:72` and `:121`.
- A typed loop variable type-checks each element as it is assigned. A freed object is not a valid `Vehicle`, so the error fires before `is_instance_valid` runs.
- The log shows this: `_lane_clear:121` is the `for` line, and the old signature error shows up at `tick:73`.
- Everything after the guard (`peer.global_position`, `peer.tuning` and so on) is safe only because freed entries are skipped before that point.

I couldn't run Godot. I didn't confirm whether the log came from before the Variant edit. The loop-variable behaviour is from my knowledge of GDScript typing, not from a test run.

**Fix:** iterate with an untyped variable, guard it, then bind a typed local after the guard. Apply the same change at both sites.

```diff
--- a/godot/scripts/cpu_racecraft.gd
+++ b/godot/scripts/cpu_racecraft.gd
@@ tick
-	for peer: Vehicle in peers:
-		if not _relevant(peer):
+	for candidate: Variant in peers:
+		if not _relevant(candidate):
 			continue
+		var peer: Vehicle = candidate
 		var relative := peer.global_position - _vehicle.global_position
@@ _lane_clear
-	for peer: Vehicle in peers:
-		if not _relevant(peer) or peer == excluded:
+	for candidate: Variant in peers:
+		if not _relevant(candidate) or candidate == excluded:
 			continue
+		var peer: Vehicle = candidate
 		var relative := peer.global_position - _vehicle.global_position
```
