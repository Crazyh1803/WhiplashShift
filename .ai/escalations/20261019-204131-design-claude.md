**Recommendation: build one visual-only road ribbon for the whole loop, drawn with one `ShaderMaterial`, and keep the per-run collision bodies exactly as they are.**

Right now `_build_run` (track_builder.gd:181–223) feeds the same `verts` array to both the mesh and `ConcavePolygonShape3D.set_faces`.

1. **Separate the two.** Keep `_build_run` and its `verts` array unchanged, but either stop it creating a `MeshInstance3D` or hide that mesh. Collision output stays byte-identical.
2. **Add a `build_road_visual(parent, pts)` that walks the closed loop once.** It writes:
   - **Position:** the same edge maths as the collision, offset +0.02 in Y.
   - **UV:** `u` across the road from −1 to 1. `v` is cumulative centreline arc length in metres, not normalised. Arc length on the centreline keeps markings at a steady spacing through corners.
   - **COLOR.rgba / CUSTOM0:** a weight for each surface, so there are 8 slots, one per surface ID. At each change of surface ID, crossfade the weights over about 3–4 m in `v`. That removes the hard seam at every run boundary. It's visual only: the wheel raycast still reads the run's `surface_type` metadata.
   - **Loop closure:** the start/finish line hides the `v` wrap. Snap the marking period so the total length is a whole number of periods.
   - **Indexed mesh** (`SurfaceTool.index()`) so seam vertices are shared.
3. **Shader cost.** Use one `NoiseTexture2D` (256², `seamless = true`), generated at runtime so it isn't a bitmap asset. Sample it at two scales in world XZ for aggregate, ruts, puddle masks and cracks; world-space sampling avoids stretching where UVs compress on the inside of corners. Blend surfaces with the weights, not with `if` branches. Ice, water and puddles only lower roughness, with no SSR. Markings and wheel paths are analytic `smoothstep`s on `u` and `fract(v / period)`. That comes to about 2 texture reads and roughly 60 ALU per pixel.
4. **Shoulders.** Use a second strip on the same material from `w/2` to `w/2 + RAIL_OFFSET + ~2 m`. It shares the road's edge vertices and drops to y ≈ 0.01 at its outer edge, so nothing sits coplanar with the road or the ground.
5. **Posts and scenery.** Use one `MultiMeshInstance3D` per prop type, with `visibility_range_end` set and no collision nodes. Generalise `_warning_clearance` (track_builder.gd:161) to take a radius, and reject any prop within `w/2 + RAIL_OFFSET + radius + margin` of **any** segment. That also covers other stretches of the loop that pass close by. Also reject props near approach-board positions. Use an XZ grid hash if prop counts grow past a few hundred.
6. **Lighting.** `ProceduralSkyMaterial`, one directional light with `directional_shadow_max_distance` around 150, and depth fog. No SSAO, SSR, glow or volumetrics.

**Main tradeoff:** a second road mesh adds a little memory and build time, and a shader to maintain, compared with tweaking `_material()`. In return you get continuous seams, one draw call, and a collision path that is never touched.

**Alternative worth considering:** keep one mesh per run and swap `StandardMaterial3D` for triplanar detail. It's simpler, but the hard material seams stay and you get one draw call per run.

**Risks:**
- **Raycasts.** Anything new that has a collider (a `StaticBody3D` or `CSG` with collision on) can catch the wheel raycasts, which would lose `surface_type`, as well as CPU racecraft and item probes. Make every prop a plain `MeshInstance3D`/`MultiMesh`, and test it.
- **Collision invariance test.** Compute a golden fixture on the current HEAD: face count plus a quantised hash of `shape.get_faces()` for each `Run_*`. Assert the hash is unchanged, and that run names and metadata match too.
- **Proving ground.** `build_proving_ground` also calls `_material()`. Leave it alone or move it over deliberately.
- **Noise loads asynchronously.** `NoiseTexture2D` generates in the background, so await `changed` before the capture fixture runs, or the captures won't be deterministic.
- **Vulkan shader hitch.** The first frame that draws the new shader can stall while it compiles. Render the material for one warm-up frame during loading, and check the headless `--rendering-driver vulkan` log for errors.
- **Tight corners.** Where the corner radius is smaller than `w/2 + shoulder`, the inner shoulder folds over itself. Clamp the inner offset and add a numeric check that triangle areas stay positive.
