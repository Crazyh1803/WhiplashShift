**Recommendation: keep the race-owned `RaceItems` controller. Make it the single owner of combat state, and add a cheap track-space gate so shots stay on their own track section.** The isolation is right: `proving_ground.gd` drives `setup`, `reset`, `reset_racer` and `tick`, and neither vehicle handling nor standings knows about items. The remaining problems are a few lifecycle loose ends and one gap in the collision model.

**Lifecycle**
1. **Impact flashes freeze outside racing.** `tick()` returns early when the state isn't RACING (`race_items.gd:95-97`), so flashes stop mid-animation on screen through RESULTS. Either free `effects` inside `_clear_shots()` or keep ticking effects before the state check.
2. **Recovery detection is split.** The player's recovery calls `items.reset_racer(0)` at `proving_ground.gd:277`, but CPU recovery is found by comparing `recoveries` counters (`proving_ground.gd:363-366`). A CPU recovery that happens on the same frame as a hit is only caught a frame late. Prefer a `recovered` signal on `CpuDriver` that `RaceItems` connects to in `setup`. That gives one way to handle recovery and removes `_item_cpu_recoveries`.
3. **The F2 debug freeze affects combat.** `available()` checks `freeze`, so pressing F2 also deletes in-flight CPU shots. That's acceptable for debug, but document it or test against `_retired` instead.
4. **`setup()` isn't idempotent.** A second call would duplicate pickups. Guard against it or assert.
5. **Retired owners' shots vanish mid-air** (`race_items.gd:166`). This is fine for "retire finished racers", but it's an intentional rule, so put it in a test.

**Collision (the main risk)**
- **Shots inherit the car's pitch.** `forward_vector()` includes pitch (`vehicle.gd:604`), so on crests and dips the shot ray hits the road surface within metres. The CPU check uses the same vector, so this kills shots for both sides. Fix it by projecting the direction onto the local track plane (the course point `dir`). Alternatively, give `_ray` a `collision_mask` covering only vehicles and guardrails, not the drivable surface.
- **Adjacent sections aren't actually prevented.** The plan says shots must not cross into adjacent track sections, but the code only stops them where a physical wall happens to block the ray. On open hairpins or switchbacks, a 140 m straight shot can hit a car on a different section. That covers both the player's hits and CPU target picking (`_cpu_has_shot` checks only straight-line distance, 7–95 m).
  - **Fix:** in `_apply_hit` and in `_cpu_has_shot`, require the victim's distance along the track, relative to the owner, to be between 0 and about 120 m. You can read that from `race.entrants[i]["progress"]`.
  - **Tradeoff:** this removes "lucky" cross-track hits. For readable solo arcade play that's the right call.
  - **Alternative worth considering:** a corridor check that expires a shot once its lateral distance from the course centreline exceeds `w/2 + margin`. It's more physical but costs more per frame.
- **The player wins pickup ties.** The pickup loop breaks on the first car in index order (`race_items.gd:109-126`), so the player beats a CPU when both reach a pickup in the same frame. This is minor, but it bends "identical CPU rules". If you care about parity, pick the car with the closest sweep point.

**Solo scope**
- The scope holds: one held item, one projectile, no health, and impulse-only disruption. Don't let a second item type into this controller yet. If one comes, change `held: Array[bool]` to an item-id enum first, and not before.
- Watch whether a hit's speed loss trips the CPU stuck/recovery heuristic. If it does, every hit turns into a teleport, which feels like a bug. Add a regression test that a hit CPU doesn't increment `recoveries` within `HIT_PROTECTION`.

**Risks to existing systems**
- `_retire` sets `collision_layer = 0`. Retry has to restore it before `items.reset()`. It looks ordered correctly at `proving_ground.gd:227-240`, but nothing tests it.
- The impulse acts on the rigid body behind `Vehicle`'s cached `speed`/`fwd_speed`. Make sure the HUD and the whiplash logic don't read stale values for a frame.
