**Root cause (probable, not provable from the logs): the leaked ref is held by the engine, not by your scripts.**

- `vehicle_audio.gd:95-99` already drops every script-side reference. That covers `_engine_playback`, the player's stream, and the local `generator` at line 38, which goes out of scope.
- `AudioStreamPlayer.stop()` doesn't release the playback straight away. The `AudioStreamPlayback` object sits in `AudioServer`'s bus playback list (`AudioStreamPlaybackListNode`) until the audio mix thread runs and prunes it. `AudioStreamGeneratorPlayback` is a RefCounted, so that list holds its refcount of 1.
- Your fixture runs a few frames and then quits. Nothing mixes after that: `verbose-run.log` shows `PulseAudio: context terminated` before shutdown. The mixer never gets another pass, and the playback is still listed when ObjectDB is torn down. That matches "exactly one refcount-1 `AudioStreamGeneratorPlayback`, no Node leaks".
- This also explains the WeakRef result. A WeakRef assertion changed the timing and ordering, which hid the leak. That's evidence the leak is timing-dependent, not a bug in your code.
- `.ai/captures/terrain/verbose-run.log` has no leak line in its last 15 lines or in the AudioStream/leak greps. I'm inferring the playback leak from your description. I haven't seen it in the log.

**A further `stream = null` change won't help.** You already do that at line 98, and it only removes the player's reference to the stream. The mixer list's reference to the playback is a separate one. Further code patches to `vehicle_audio.gd` have low expected value.

**Smallest patch:** make the fixture give the mixer time to prune before it quits. If that doesn't work, accept the leak as a known engine artifact.

```diff
--- a/godot/tests/race_visual_qa.gd
+++ b/godot/tests/race_visual_qa.gd
@@ -26,6 +26,9 @@
        _scene.queue_free()
        ...
        _check("terrain fixture frees race before shutdown", not is_instance_valid(_scene))
+       # Let AudioServer's mixer thread prune the stopped playback before exit.
+       await get_tree().create_timer(0.3).timeout
        get_tree().quit(1 if _fail else 0)
```

The 0.3 s is a wall-clock wait, which is what the mixer needs. Frame-based awaits don't help, because headless frames can run much faster than the audio thread.

**Verify:** run the fixture with `--verbose` and check whether the `AudioStreamGeneratorPlayback` refcount line disappears.

**If the leak persists after the wait**, check these in order:
1. **Audio driver.** Run with `--audio-driver Dummy`. If the leak disappears, the PulseAudio shutdown ordering is the cause. If it still leaks, the dummy driver mixes only when the server is active, so the cause is the same one: the engine never prunes the playback.
2. **Playback node.** Call `_engine_player.stop()` and then `remove_child(_engine_player)` and `_engine_player.free()` in `_exit_tree`, instead of leaving the player to `queue_free` with its parent. This removes the player's own `stream_playbacks` reference sooner.
3. **Accept it.** If 1 and 2 don't clear it, the leak is a Godot shutdown artifact. It is a single object, it only appears on exit, and it has no gameplay impact. Don't chase it further. Add a comment in `race_visual_qa.gd` documenting it, and don't assert on it.
