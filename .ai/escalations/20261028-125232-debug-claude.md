I couldn't reproduce the failure, because this run was read-only and the Godot test can't be run here. So I can't name a single root cause with log evidence. What the code does show:

**Ruled out by the code**
- **Recovery stall:** the pilot's own recovery (`cpu_driver.gd:110`) fires on 6 s below 1 m/s, 3 s off the ribbon, a flip or a fall. `recoveries=0` with 537 s elapsed means the pilot never hit any of these. It kept moving for the whole run.
- **Pure time loss:** a 216 s run versus a run that is still unfinished at the 540 s cap (64800 ticks at 120 Hz) is not slowness. `RaceDirector.tick` (`race_director.gd:45`) ends the race only when `player_progress.lap >= 3`, so the pilot must be failing to score laps.
- **Rival hits:** the rivals' CPU weapons (`race_items.gd:42`, an unseeded `RandomNumberGenerator`) are the only nondeterministic input in a run that is otherwise fixed-step. Hits would cost seconds or trigger a recovery, though. They wouldn't produce a 2.5× overrun with no recovery.

**Ranked hypotheses**
1. **`TrackProgress` loses its lap or checkpoint state while the pilot keeps driving (most likely).**
   - A lap counts only if `_lap_travel > 0.9 * total_length` and `_next_checkpoint == checkpoints.size()` (`track_progress.gd:96`). Both reset at every line crossing (`:98-99`), so one missed checkpoint costs one whole lap of about 72 s. The 537 s run missed repeatedly.
   - The checkpoint loop breaks as soon as `checkpoint_distance <= distance` (`:92`), so a checkpoint that is skipped once is never advanced for the rest of that lap.
   - `update()` also returns early without moving the anchor when `|delta| >= 100` or `off_line >= 0.65 * w` (`:77`). A swap spin, a corner clip or a rival bump can trigger that.
   - Because `update()` reads and writes only its own tracker, the pilot's `progress` and `scene.player_progress` can disagree. The pilot's recovery triggers read only its own tracker. A frozen or odd `player_progress` is therefore invisible to the pilot, and the test never asserts the two trackers agree.
   - Block Circuit's checkpoint list or tight corners may make this more likely than on Split Shift.
2. **Rival interaction.** A weapon hit or a blocked lane can push the pilot onto a different line each run, which would make the checkpoint miss intermittent. Seeding the rival weapon rolls tests this directly.
3. **Harness mismatch (least likely).** The pilot at priority 200 updates its tracker after the scene's tracker has run for that tick, but both read the same car position. This is a one-tick offset at most and can't explain a persistent miss.

**Suggested patch:** seed the item RNG and log tracker state to tell these apart. It does not touch physics or loosen any assertion.

**How to verify**
1. Run the test about 5 times with the seed fixed.
   - If it passes every time, hypothesis 2 is confirmed. Keep the seed, then run a few other seeds to check the course isn't marginal.
   - If it still fails intermittently, the rolls aren't the cause.
2. Read the `CITY_DIAG` lines on a failing run.
   - `next_cp` stuck below the checkpoint count while `lap` stays flat means a checkpoint was skipped (hypothesis 1).
   - `dist` and `off` frozen while `spd` is high means the `update()` early-return anchor has locked (hypothesis 1).
   - `lap` differing between the pilot's and `player_progress`'s trackers also points to hypothesis 1.
3. When it fails, print the checkpoint distances from `block_circuit_data.gd`. Compare them with the car's position at the lap crossing. A checkpoint sitting inside a tight corner or on the swap boundary is the likely culprit.

If hypothesis 1 holds, the real bug is in `TrackProgress`, not the course geometry. Fix it there, not in the test.
