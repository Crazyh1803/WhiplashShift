**Diagnosis (read-only, nothing measured at runtime).** Temporal sampling is the most likely cause. Frame pacing and GPU load are not ruled out until you measure.

**Evidence**
- `godot/project.godot:36` sets physics to 120 Hz. `physics/common/physics_interpolation` is not set, so it is off.
- `camera_rig.gd:34,50,52` runs in `_process` and reads `target.global_position` and `forward_vector()` (`vehicle.gd:604`). Both come from the last physics tick.
- Physics ticks per rendered frame are 0, 1, 2 or 3 at any refresh rate that isn't a multiple of 120 Hz. The car's transform then advances unevenly from frame to frame. The rig's exponential lerp (`camera_rig.gd:50`) turns that into a visible stutter.
- `_integrate_forces` writes the axle position (`vehicle.gd:680`). The wheel's `_place_visual` (`wheel.gd:218-222`) is called from the same physics step. Those children are also stepped at 120 Hz.

**How to separate the causes before changing anything**
1. Run windowed and uncapped with the real renderer. Log `Engine.get_frames_per_second()` and per-frame `delta` for 10 s, along with the physics ticks that ran in each `_process` call. Count them by incrementing in `_physics_process` and resetting in `_process`.
   - If `delta` is steady, the tick counts alternate (for example 1, 2, 1, 2), and the jitter is visible, the cause is temporal sampling.
   - If `delta` spikes (more than about 1.5× the median), the cause is frame pacing or GPU load. Interpolation won't fix that.
2. Use `Performance.get_monitor(RENDER_TOTAL_DRAW_CALLS_IN_FRAME)` and `RenderingServer.get_frame_setup_time_cpu()` to check the GPU side. Check the active renderer with `RenderingServer.get_current_rendering_method()`.
3. For a quick A/B test, set `physics_ticks_per_second` equal to the display rate. If the jitter disappears, it is sampling.

**Proposed fix.** Turn on built-in interpolation and have the camera read the interpolated transform. Handling and physics are untouched.

```diff
--- a/godot/project.godot
+++ b/godot/project.godot
@@ [physics]
 common/physics_ticks_per_second=120
+common/physics_interpolation=true
 3d/physics_engine="Jolt Physics"
```

```diff
--- a/godot/scripts/camera_rig.gd
+++ b/godot/scripts/camera_rig.gd
@@ func _ready() -> void:
+   # The rig and its camera move in _process and sample the interpolated car, so
+   # they must not be interpolated a second time.
+   physics_interpolation_mode = Node.PHYSICS_INTERPOLATION_MODE_OFF
    cam = Camera3D.new()
@@ _ready
    if target:
-       global_position = target.global_position
-       var f := target.forward_vector()
+       var xf := target.get_global_transform_interpolated()
+       global_position = xf.origin
+       var f := _forward(xf)
@@ func _process(delta: float) -> void:
-   var f: Vector3 = target.forward_vector()
+   var xf := target.get_global_transform_interpolated()
+   var f: Vector3 = _forward(xf)
@@
    global_position = global_position.lerp(
-       target.global_position + lead, 1.0 - exp(-7.0 * delta))
-   cam.look_at(target.global_position + Vector3.UP * 0.75)
+       xf.origin + lead, 1.0 - exp(-7.0 * delta))
+   cam.look_at(xf.origin + Vector3.UP * 0.75)
+
+
+func _forward(xf: Transform3D) -> Vector3:
+   return xf.basis * Vector3(0.0, 0.0, -1.0) * target.forward_sign()
```

**Resets.** Call `reset_physics_interpolation()` immediately after each discontinuous placement so the car doesn't streak from its old pose. It recurses into the wheel and axle children.

```diff
--- a/godot/scripts/proving_ground.gd  (_place_player, after the three PhysicsServer3D.body_set_state calls)
+   car.reset_physics_interpolation()
+   rig.global_position = transform.origin
```

```diff
--- a/godot/scripts/cpu_driver.gd  (_place, after the body_set_state calls, line ~178)
+   target.reset_physics_interpolation()
```

- `_place_player` covers spawn, `R` recovery and retry, because `restart_race` calls `_respawn` (line 216) and `driver.reset` (line 219) → `_place`.
- Snapping `rig.global_position` in `_place_player` is optional. Without it the camera swoops across the track on recovery. That is existing behaviour, so drop the line if you want zero behaviour change.
- In `restart_race`, entrants are re-shown with `entrant.visible = true` (line 207). Add `entrant.reset_physics_interpolation()` after the placements, so a CPU car re-shown at its old pose doesn't interpolate from it.
- `reset_physics_interpolation()` must run after the transform is assigned. Placing it after `global_transform = transform` and the `body_set_state` calls satisfies that.

**Garage preview.** `garage.gd:445,451,535` set `_preview_vehicle.rotation.y` from the frame-driven code, with the vehicle frozen. With global interpolation on, a transform set outside the physics tick is only picked up at the next tick, so the preview would turn in 120 Hz steps. Opt it out where it is created, near `garage.gd:403` and `:531`:

```diff
+   _preview_vehicle.physics_interpolation_mode = Node.PHYSICS_INTERPOLATION_MODE_OFF
```

Do the same for any other frame-driven preview Node3D, such as turntable or visual-QA fixtures that set transforms in `_process`.

**Risks**
- Frozen test fixtures such as `race_visual_qa.gd` and `cpu_tests.gd`, which set `global_transform` directly, may need `reset_physics_interpolation()` if they compare rendered positions. The headless logic tests are unaffected, because `global_transform` is the raw physics state.
- `get_global_transform_interpolated()` lags the physics state by up to one tick, about 8 ms. That is a small, constant presentation delay.
- Only the sampling of the car's wheel and axle visuals changes. Nothing physical does.

**Verify**
1. Run `ak-test`.
2. Re-run the step 1 log at ordinary runtime timing, before and after. Tick counts per frame will still vary, but the on-screen car-to-camera offset should be steady. Log the camera-to-car distance per frame and check that its variance drops.
3. Check by eye: recover with `R`, restart with Enter, and open the garage and rotate the preview. Look for a streak or a stepped turn.

**Alternatives if sampling is not the cause.** Rank these by what step 1 shows:
1. `delta` spikes point to a GPU or driver cost. Check MSAA 2× (`project.godot:41`), the renderer and the shadow settings.
2. A steady `delta` with visible jitter, but with interpolation already on, points to a missing reset or a node not inheriting interpolation.
