**Recommendation: yes, the subclass is safer than editing base `Vehicle`, with two changes to the proposal.** I have not run any of this; it is from reading the code.

Physics isolation holds: the overrides only touch visual hooks, bogie wheels never enter `wheels`, and mass and inertia are explicit (`vehicle.gd:280-292`).

**Change 1: guard on a catalog flag, not `vehicle_id == "blackjack"`.**
- `vehicle_id` defaults to `"blackjack"` (`vehicle.gd:24`), and both the garage and the race call `add_child` before `apply_vehicle_spec` (`garage.gd:388`, `proving_ground.gd:83-84`, `:104-105`).
- So the first `_build()` runs with the guard true and an empty `_visual_config`, for every vehicle.
- Wheels then get placeholder visuals, and `_update_axle_visuals` dereferences a null `get_node("ModularWheelVisual")` (`blackjack_blueprint_preview_vehicle.gd:69-72`).
- Use something like `_visual_config.get("rig") == "blackjack_blueprint"`, which is false by default. Have the factory call `apply_vehicle_spec` before `add_child`, which also gives a single build.

**Change 2: the garage re-creates the preview through the factory when the ID changes, instead of morphing one guarded instance.**
- `_refresh_customization_preview` already branches on ID change (`garage.gd:499`).
- Free the old preview, create the new one, and reapply `freeze`, the collision layers, `process_mode` and `_preview_yaw`.
- This removes the whole "clean up blueprint state when leaving blackjack" problem.

**Lifecycle hazards**
1. **Suspension links never appear in the garage.** `supports` are built and posed only in `_process`, which never runs under `PROCESS_MODE_DISABLED` (`garage.gd:387`). Move the build and pose into a function called at the end of `_build_visual_bogie`; `_process` then only re-poses.
2. **Stale links.** `supports` are children of the vehicle, not `_visual_root`, so they survive rebuilds. If you keep the morphing design they stay visible on other chassis. They also float when the wheel style is embedded, because wheels are hidden but links are not.
3. **Null dereferences on style change.** The blueprint `_process` (line 93) and `_update_axle_visuals` use `get_node` without a null check. Any style with a missing wheel scene will crash.
4. **Decals are lost on every paint tick.** `add_livery_decal` parents to `_visual_root`, which `_rebuild_visuals` frees on each `apply_customization` (`vehicle.gd:102-104`). Store the decal specs and re-add them in a `_rebuild_visuals` override. Also check the renderer: decals do not work in Compatibility.
5. **Wheel scale survives only by call order.** `set_visual_scene` recreates the assembly, and the subclass re-runs `_install_tire` after `super`. Keep that order.
6. **Script location.** A production script must not extend `res://tests/...`. Flatten the two test classes into one file under `scripts/`, drop the unused refined `TIRE_SCENES` preloads, and leave the test files as thin `extends` shims.
7. **Duplicated geometry constants.** `DISPLAY_TRACK - tuning.half_track` ignores catalog `wheel_mounts` and overwrites `assembly_offset_a/b`. Move the display radius and track into the catalog's visual block.

**Main tradeoff:** the subclass depends on base private hooks and their call order (`_build_axles` → `_update_axle_visuals` → `_update_visual_bogie`), so base refactors can silently break the art.

**Alternative worth considering:** a composed `VehicleVisualRig` child node with its own `_process` and no overrides. It is cleaner but needs new hooks in `Vehicle`, which is the internals change you are trying to avoid. Defer it until a second vehicle needs a rig.

**Verification to add:** a parity test that drives base `Vehicle` and the subclass with identical scripted inputs for N physics steps and asserts identical transforms and velocities, plus a garage test that cycles all IDs and wheel styles with processing disabled.
